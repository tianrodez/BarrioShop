# Prototipo evolutivo BarrioShop — feature document

Objetivo: construir desde cero el prototipo evolutivo de alta fidelidad de BarrioShop que satisfaga las 11 HU de `historias-de-usuario.md`, con los mejores patrones y testing, sobre el stack confirmado.
Branch: `feat/hu02-store` (worktree aislado de la revisión U2 pendiente).
Delivery: local work-unit commits (~400 líneas authored por unidad); sin push/PR hasta decisión del equipo. Runner: `npm test` (Vitest).

## Specs

- **S1** (petición del usuario, textual): "Realmente quiero que tu lo construyas, no vamos a usar lovable, pero si construirlo desde cero nosotros con tu ayuda. Como el prototipo es evolutivo y de alta fidelidad me parece que puntuamos doblemente para el prototipo y luego cuando ya sea la entrega final tenemos ya mucho avanzado."
- **S2** Stack confirmado por el usuario tras evaluar Next.js vs Vite ("Si, te confirmo esa eleccion."): Next.js 16 (App Router) + TypeScript + Tailwind v4 + shadcn/ui + Supabase (Auth, PostgreSQL+PostGIS, Storage, RLS) + Leaflet/OSM/Nominatim + Vercel (región São Paulo). Vercel no es solo hosting: §29 de la formulación lo define como runtime del backend "como funciones".
- **S3** (petición textual): "Adicionemos que hagas un todo.md, un readme.md del proyecto y tambien un avances.md, pero esos de momento dejarlos en el gitignore." Los tres archivos existen localmente y están en `.gitignore`; README debe salir del ignore antes de la entrega final (RNF-08) — anotado en README y todo.md.
- **S4** (petición textual): "ejecutalo todo de forma correcta, con los mejores patrones, testing y demas para este prototipo evolutivo." ⇒ ESLint strict + Prettier, typecheck, ciclo RED→GREEN con Vitest/Testing Library para cada comportamiento determinista, estructura por capas (`app/` rutas, `lib/supabase` acceso a datos, `components/ui` shadcn), migraciones SQL versionadas.
- **S5** El contrato de comportamiento son las 11 HU de `historias-de-usuario.md` (HU01–HU11 con sus criterios y trazabilidad). Restricciones vinculantes de la formulación: §29 (claves nunca en el navegador; anon key + RLS como patrón; imágenes ~500 KB; Nominatim solo a demanda), §8 (roles en tabla dedicada), RNF-02 (aislamiento por tienda en backend), RNF-04 (<3 s), HU08 (responsive). Decisión explícita del usuario: "conservar los reportes por favor" — borrar un producto no debe eliminar sus reportes asociados; deben conservarse con contexto suficiente para la revisión administrativa. U4 aplicará borrado lógico (`deleted_at`) para mantener la relación producto-reporte; RLS oculta productos borrados al público y conserva acceso de moderación.
- **S6** Todo commit de unidad deja el repo con `npm run typecheck && npm run lint && npm test && npm run build` en verde; verificación observable se registra en este Log.
- **S7** (petición textual): "Listo, sigamos con las demas HU y elimina el uso de supabase local ya que tenemos la API." La app debe usar el proyecto Supabase hosted proporcionado como backend de desarrollo; no debe depender del Supabase local. Las migraciones y verificaciones SQL permanecen versionadas y aisladas del proyecto hosted.
